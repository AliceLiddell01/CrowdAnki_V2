# Руководство для ИИ-агентов (CrowdAnki V2)

Данный документ определяет ключевые архитектурные правила, стандарты и ограничения проекта. Любой ИИ-агент, работающий в репозитории, обязан строго следовать изложенным положениям.

---

## 1. Назначение и архитектурная модель проекта

- **CrowdAnki V2** — новый аддон для актуальных стабильных версий Anki, разрабатываемый с нуля (не форк и не модернизация устаревшего кода).
- **Go — основной язык проекта**: вычислительное ядро, обработка форматов, синхронизация и бизнес-логика реализуются на Go (`core/`).
- **Python — тонкий адаптер**: минимальный слой интеграции с API и интерфейсом Anki/Qt (`addon/`). Бизнес-логика в Python не переносится.
- **PowerShell 7 (`pwsh`)**: кроссплатформенные служебные сценарии сборки, проверок и локальной автоматизации (`build/`).
- **Запрет прямой записи в базу данных**: любые изменения коллекции Anki должны выполняться исключительно через поддерживаемый публичный API Anki, а не через прямые SQL-запросы к SQLite.

---

## 2. Критические стандарты разработки

### Языковая политика
- Весь человекочитаемый контент проекта **строго на русском языке**: документация, комментарии в коде, docstrings, сообщения об ошибках, тексты сценариев, сообщения коммитов, названия веток и описания PR.
- Общепринятые технические идентификаторы (имена стандартных файлов, ключевые слова языков, типы внешних API, `manifest.json`, `go.mod`, `GOOS`/`GOARCH`) сохраняют оригинальный технический вид без искажений.

### Запрет именования по этапам разработки
- В репозитории категорически запрещены названия и термины вроде `stage1`, `phase2`, `step3`, «этап 1», `first_phase` и аналогичные.
- Все сущности (ветки, файлы, пакеты, типы, функции, коммиты, тесты) именуются **исключительно по своему назначению и ответственности**.
- Запрещено ведение roadmap и планов будущих этапов внутри репозитория.

### Единый источник истины и запрет хардкода
- Метаданные пакета (имя, идентификатор, версии) хранятся в `build/config.json`.
- Версия Go фиксируется в `core/go.mod`.
- Версия Python фиксируется в `.python-version`.
- Не дублировать конфигурационные параметры по файлам проекта без технической необходимости.

### Простота и минимизация зависимостей
- Никаких лишних абстракций, фабрик без причины, gRPC/Protobuf, микросервисов, Docker и баз данных внутри репозитория.
- Не подключать сторонние библиотеки в Go и Python без предварительного технического обоснования.
- Не заниматься несвязанным рефакторингом стороннего кода при решении конкретной задачи.

### Честность инструментов качества
- Запрещено маскировать ошибки отключением правил линтеров (`ruff`, `go vet`, `PSScriptAnalyzer`) ради формально зелёного CI.
- Если обнаружена реальная несовместимость правила, допустимо точечное подавление с обязательным комментарием-обоснованием.

## 3. Регламент Git и контроля качества

1. **Запрет работы напрямую в ветке `main`**:
   - Любая задача выполняется в отдельной ветке, созданной от актуального `main` (например, `инфраструктура/подготовка-репозитория`, `сборка/пакет-аддона`).
   - Изменения попадают в `main` только через Pull Request.
2. **Обязательные локальные проверки перед оформлением PR**:
   - Запустить единый сценарий проверок: `pwsh -File build/check.ps1`.
   - Убедиться в чистоте рабочего дерева Git (`git status`).
3. **Синхронизация документации**:
   - При любых изменениях логики сборки, параметров окружения или структуры репозитория незамедлительно актуализировать `README.md`.
